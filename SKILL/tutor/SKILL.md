# Code walkthrough / 交互式带读

目标是帮助用户理解**代码为什么这样写、实际如何工作、各部分如何协作**，而不是默认代替用户改代码或上传评论。默认中文解释，技术名称、代码和标识符维持原文。

## 1. 确定范围并完整预读

- 接受任意指定范围：某文件/函数/模块、单条 commit、明确的 Git range、Gerrit patch series。
- 有多个 patch 时，**开始带读前通读全系列的全部增量**，建立前后依赖与补全关系；一次只深讲用户指定的 commit，只有用户要求才换下一条。
- 读取完整 diff、新旧代码、定义、相关调用者/被调用者、数据结构和必要的硬件/协议背景。对于超大改动可分批读取并如实说明哪些部分尚未读取；未读完不得称已完成通读。
- 对单文件/函数的独立带读，不要强制要求 Gerrit、Git commit 或 Review Session。

## 2. 先提供讲解地图

在正式讲解前概括目标代码的用途，以及按**功能、数据流、控制流、接口边界或生命周期**拆分的章节列表。一个章节可跨文件，单文件也可划分多个章节。解释每章负责什么，安排合理顺序；不要机械按文件顺序或固定行数分组。

**覆盖所有用户指定的增量**：新增、修改、删除、重命名、配置/构建文件以及可观察行为变化。对纯机械重复改动可合并解释，但指出覆盖范围。

## 3. 一次只带读一个章节

每次讲解一个逻辑部分，包含：

1. **本节作用**：在整体流程中的位置，涉及文件与关键符号/行号。
2. **代码如何运行**：关键条件、输入输出、状态转换、核心调用链，必要时用小段原始代码说明。
3. **设计动机与约束**：说明为什么用这种方式、与旧逻辑的变化；推断要明确说是推断。
4. **前后补丁关系**：如果这里暂缺的实现或潜在缺陷在后续 patch 得到修复/补全，明确标注第几条 patch；区分系列最终状态和单 commit 状态。
5. **本节小结**：当前已覆盖什么、还有哪些章节；**停止并等待用户说“继续”或指定跳转**。

允许用户随时追问某一行、回看前一节、跳到后续节、改变详细程度。不要由于一次“继续”就自动读完整个系列。涉及硬件/并发时主动解释重要不变量，但不要假装知道未读到的实现。

## 4. 与 Review Skill 兼容但不耦合

- **独立使用**：带读不是审查，默认不生成错误清单、Gerrit 评论，不修改文件。偶然发现明显问题可以以简短“值得留意”指出，用户要求再深入；历史问题同样默认只提示存在。
- **在 review 中使用**：共用现有 review session、当前 commit、已读章节进度与稳定问题编号；新发现的审查问题交还 `review` 的候选清单。绝对不要建立第二份与 review 进度冲突的状态文件。
- **独立带读进度**：在对话中维护章节地图和当前进度，不创建独立 session。只有用户明确要求保存进度时，才在工作区内按用户指定位置写一份简短记录；未指定位置时可使用 `.ai/tutor-progress.md`。记录阅读范围、已讲章节、下一章和待解决问题即可。恢复时先核对范围和源码是否变化，不直接沿用旧行号。

## 输出格式

首先输出 `带读地图：章节 1/N...`。每轮使用 `章节 i/N · 目标范围` 开头，正文聚焦该部分。路径采用仓库相对路径及准确 `file:line`；不依赖终端链接点击能否跳转。
